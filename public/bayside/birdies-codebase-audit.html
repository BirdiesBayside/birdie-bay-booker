How to use this document

  1. Read the customer's Sim Centre Onboarding Questionnaire JSON answers first. Wherever a section below is marked From questionnaire, the value comes from those answers.
  2. Walk through sections 1–16 in order. Each section says where the value lives and what to replace it with.
  3. Never bulk find-and-replace blindly across supabase/functions/ — many values appear inside HTML email strings where surrounding markup must stay intact.
  4. The Birdies database schema is generic enough that no schema changes are required for white-labelling. Only seed data and config values change.
  5. The supabase/migrations/ folder is auto-managed — do not hand-edit historical migrations. Use new migrations for any schema additions the customer needs.
Conventions used below: From questionnaire = answer-driven · Manual review = re-read the surrounding code, don't blind-replace · Optional = only if the customer wants the feature.

1. Brand identity From questionnaire

Birdies uses HSL semantic tokens. Replace these and every component will update automatically — never hardcode hex values in components.

Birdies pairs Anton (display, uppercase) with Inter (body). Loaded via Google Fonts in index.html.

  • index.html — the <link> tags loading Google Fonts.
  • tailwind.config.ts — the fontFamily map.
  • Email templates (see §14) — fonts are inlined as Google Font URLs inside HTML strings.

Logos & favicons

  • Replace logo files in src/assets/ (imported as ES modules) and any in public/ referenced by emails.
  • Replace public/favicon.ico and any og-image.
  • Update <title>, meta description, OG tags in index.html.

Special colour rule

Birdies uses blue for over-par scores on leaderboards (everywhere else green = under, red = over is replaced by green = under, blue = over). Confirm with customer before changing — many golf venues prefer this.

6. Pricing rules From questionnaire Manual review

Two layers:

  1. Code-level constants & logic in src/lib/pricing-utils.ts:
    • VISITOR_PEAK_RATE = 35
    • VISITOR_OFF_PEAK_RATE = 30
    • isPeakTime() hardcodes "Fri/Sat/Sun all day + Mon–Thu 4pm onwards" — re-write to match the customer's peak/off-peak definition.
    • isWeekdayMemberTime() hardcodes "Mon–Thu before 4pm" for the Weekday tier — only relevant if the customer keeps a weekday-style tier.
    • Tier branches in calculateHourlyRate() reference 'visitor', 'weekday', 'birdie', 'eagle' — must match the tier keys in §7.
    • Staff free-play rule: options?.segment === "staff" grants free off-peak. Confirm customer wants this.
  2. Database-driven prices in the pricing_config table (per-tier hourly rate, weekly subscription price, Stripe product/price ids, display name, display order). Seed this table from questionnaire answers after the corresponding Stripe products exist (see §13).

src/pages/Booking.tsx has a fallback literal : 35; // VISITOR_PEAK_RATE — update if the visitor peak rate changes.

src/pages/Membership.tsx imports VISITOR_PEAK_RATE / VISITOR_OFF_PEAK_RATE for marketing copy.

Public holiday surcharge default is 20% (column default on public_holidays.surcharge_percent). Adjust per holiday row, or change the default if the customer always uses a different rate.

7. Membership tiers From questionnaire Manual review

Birdies ships four customer-facing tiers: Visitor, Weekday, Birdie, Eagle.

The database enum has additional values — do not edit the enum without a migration:

CREATE TYPE public.membership_tier AS ENUM
  ('visitor', 'par', 'birdie', 'eagle', 'albatross');

Note par and albatross exist in the enum but the active tier set in code is visitor / weekday / birdie / eagle. weekday is not in the enum literal above — verify against the latest migration before assuming.

Files that hardcode tier names:

  • src/types/booking.ts — MembershipTier type and MEMBERSHIP_TIERS pricing/feature object (display name, weekly fee, hourly rate, marketing bullets).
  • src/lib/pricing-utils.ts — branches in calculateHourlyRate().
  • src/hooks/usePricing.ts — FALLBACK_RATES mapping.
  • RLS policies on announcements, clubhouse_* tables filter membership_tier <> 'visitor' — keep visitor as the no-perks tier name or update those policies.
  • src/components/admin/MembersSection.tsx and admin membership UI list tiers explicitly.

Decision needed: if the customer wants different tier names, decide whether to (a) rename in code only and keep enum values for backwards compatibility, or (b) write a migration to add new enum values. Removing enum values is destructive — avoid.

8. Timezone From questionnaire

Hard rule for Birdies: all date logic uses Australia/Brisbane (AEST/UTC+10, no DST). Change for any customer outside that timezone.

Hardcoded in:

  • src/components/admin/SalesReporting.tsx — default useState<string>("Australia/Brisbane")
  • src/pages/admin/AdminDashboard.tsx — same default
  • src/pages/admin/AdminSettings.tsx — TZ select option list
  • src/components/admin/sgt/SGTWinners.tsx — date formatting
  • src/hooks/useActiveTourData.ts — date formatting
  • supabase/functions/first-session-promo/index.ts — admin report timestamp
  • SGT auto-register / auto-close cron schedules (6:00 AM Brisbane)

If the customer's region observes DST, audit every date comparison; the codebase assumes a fixed offset.

9. League / SGT Optional

SGT (Simulator Golf Tour) integration is specific to clubs registered with the SGT API. Most new sim centres won't have an SGT account on day one. If the customer doesn't run an SGT-style league, disable the entire feature:

  • Hide League nav items in src/App.tsx / src/components/admin/AdminLayout.tsx.
  • Skip seeding the SGT_* secrets (§12).
  • Don't schedule the SGT cron jobs in supabase/functions/.

If they do want it:

  • Set secrets SGT_USERNAME, SGT_PASSWORD, SGT_API_KEY, SGT_CLUB_URL.
  • Update the monthly 4-week block anchor in src/lib/league-block.ts (currently ANCHOR_ISO = "2026-03-01", a Sunday).
  • Confirm tournament timing rule still applies (Birdies tournaments start Sunday and end Monday Brisbane time).
  • Re-confirm prize amounts in approve-weekly-prize (defaults $40) and approve-monthly-prize functions.

10. Local competition Optional

The "weekly 2-man Ambrose" feature is fully data-driven via the local_comp_settings table:

  • default_format — currently '2-man-ambrose'
  • default_entry_fee — currently 10

The Winner's Tax handicap auto-adjustments are encoded in DB function apply_local_comp_winners_tax(): 1st = -2 (or -4 back-to-back), last = +2. Adjust deltas via a new migration if the customer wants different numbers.

11. Bay controllers & hardware From questionnaire

Files to update per customer

  • electron/main.js — WebView URLs (currently point to hub.birdiesbayside.com.au); simulator launch paths (GSPro etc.); welcome window inline HTML (4 house rules); app close whitelist.
  • electron/package.json — app name, productName, build/publish config (GitHub repo for electron-updater).
  • electron/build.bat, electron/build_tapo.bat, electron/watchdog.bat — any Birdies-named paths.
  • bay-controller.html + src/bay-controller-main.tsx — bay controller renderer.
  • src/components/bay-controller/* — branded copy, SGT overlay (omit if no league).

Per-bay PC configuration (not in repo)

  • Tapo plug IPs and bay number stored locally on each bay PC.
  • TAPO_EMAIL / TAPO_PASSWORD in Supabase secrets.
  • Windows Task Scheduler entry running watchdog.bat every 30 s.

Behavioural constants

  • Hardware ON at T-3 minutes, simulator app launch at T-1 minute.
  • App close at T-20 s, plug OFF at T+0, with 5 s intentional cooldown.
  • Back-to-back bookings skip the power cycle; T-60 s app restart prioritises the active booking, 2 min failsafe.
  • 1-minute warning notification suppressed if next booking starts within 120 s.

These timings are sensible for GSPro + Tapo P100 + typical sim PC. Confirm with customer's hardware before changing.

13. Stripe

  • API version pinned to 2025-07-30.basil across all functions. Keep aligned across charge-booking, create-membership-checkout, stripe-webhook, customer-portal, etc.
  • Webhook function (stripe-webhook) has verify_jwt = false in supabase/config.toml — required for Stripe to call it.
  • Memberships are charged immediately, no trial coupons. 1st payment failure = warning email + Stripe Smart Retry. 2nd failure = downgrade to visitor + void invoice.
  • Idempotency: random UUID suffix on identifiers allows immediate retries.
  • Refunds: duplicate payments and deleted bookings auto-refund as "duplicate".
  • Per-tier Stripe products + prices live in Stripe; ids cached in pricing_config.stripe_product_id / stripe_price_id.

Per-customer: create membership products in their Stripe account, copy ids into pricing_config, set webhook endpoint to https://<project-ref>.functions.supabase.co/stripe-webhook, store its signing secret in STRIPE_WEBHOOK_SECRET.

14. Email templates Manual review

Two layers:

  1. Hardcoded HTML inside edge functions — the customer-facing emails. These contain inlined CSS, Anton/Inter Google Font links, brand colours, logo URLs, footer addresses. Update one function at a time:
    • Logo URL (currently a Birdies asset) → customer's logo URL (host on Cloud Storage or in public/).
    • Brand colour hex values (e.g. #1F4C25, #EC622D, #FFF5E4) → customer's palette.
    • From-name "Birdies" / "Birdies Bayside" → customer name.
    • Footer address line, support email, social links.
    • Deep links to https://hub.birdiesbayside.com.au/... → customer's hub URLs.
  2. Database-stored templates in email_templates and marketing_templates — admin-editable via the Marketing UI. Re-seed with branded versions or let the customer edit them in-app.

Birdies note: email body wrappers are built on the fly per function (no shared layout file). Re-using a single helper would be a good refactor but isn't required for white-labelling.

16. Database seed data From questionnaire

The schema is generic. Only seed rows differ per customer. After remix + Cloud enable, populate via migrations or the admin UI:

public_holidaysCustomer's region's holidays + per-holiday surcharge_percent.
local_comp_settingsOne global row — format + entry fee. Optional
loyalty_promo_settingsOne global row — enable flag, visit threshold (default 5), credit amount (default $35).
pos_productsF&B menu. Optional

RLS is already wired and follows the documented model (admins via has_role(), public-read on bays/pricing/holidays/leaderboards, user-scoped on bookings/profiles). Don't loosen it without a security review.

17. Suggested execution flow for the new project's AI

  1. Ingest the customer's questionnaire JSON.
  2. Read this audit doc end-to-end.
  3. Confirm Lovable Cloud is enabled. Add all required secrets from §12 (skip optional ones if the corresponding feature is off).
  4. Apply brand pass (§1) — tokens, fonts, logos, favicons, meta. One commit.
  5. Apply config pass (§5, §6, §8) — booking config, pricing rules, timezone. One commit.
  6. Apply tier pass (§7) — only if tier names differ from Birdies; otherwise leave alone.
  7. Apply domain & email pass (§2, §3, §14) — search-and-replace with manual review of each email body.
  8. Toggle optional features (§9 SGT, §10 Local Comp, §11 Bay Controllers, §4 Mobile App) based on questionnaire answers — disable nav/cron for any "no" answers rather than leaving dead code in the UI.
  9. Seed the database (§16) using migrations checked into the new project.
  10. Configure Stripe (§13) — products, webhook endpoint, secrets.
  11. Update static pages (§15).
  12. Run the customer-facing Setup Checklist end to end and tick off the QA items.
Hard "do not touch" list: src/integrations/supabase/client.ts, src/integrations/supabase/types.ts, .env, supabase/config.toml project-level keys, historical migrations in supabase/migrations/.
